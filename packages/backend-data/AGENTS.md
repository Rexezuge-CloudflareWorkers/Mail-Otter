# Mail-Otter — Backend Data (D1/DAO Layer)

Scope: `packages/backend-data/**`. Parent index: `../../AGENTS.md`.

All D1 access via DAOs: `ConnectedApplicationDAO` (+ `ConnectedApplicationFlags.ts` flag helpers; metadata shaping extracted to `ConnectedApplicationMetadataMapper.ts` (`assembleMetadata` pure + `migrateLegacyExcludeRules` via `MetadataConfigWriter` seam); incl. `content_language` provider-config row + `updateContentLanguageForUser`), `ApplicationContextDAO` (facade over `ContextAuditLogDAO` + `ContextDeletionRunDAO`; document queries in `ApplicationContextDocumentQueries.ts`), `UserDAO` — a **subclass of `@rexezuge/identity`'s**, not a copy. Inherits the username handle (`ensureUsername`/`setUsername`/`getByUsernameCi`, migration 0029), the lowercase-parameter rule and the `null`-not-`undefined` reads. Overrides `createUser` to add the legacy-row adoption clause and to keep the kit's `null` read-back contract, and adds this repo's own `getUser` (camelCased `User`), `getRowByEmail` and `updatePreferredLanguage`. Free functions `newId()`/`newAnchor()` are module-level, `UserEmailDAO` — **a re-export of `@rexezuge/identity`'s** (the address registry; `register` refuses a _verified_ row and re-points a revoked one), `userScope.ts` (`userScopeSql(scope, alias?)` — the one ownership predicate: `user_id = ? OR (user_id IS NULL AND user_email = ?)`, plus `scopeForAnchor` for the row-carried paths and `userScopeUpsertSql` for dual-writes), `ProcessedMessageDAO`, `OAuth2AuthorizationSessionDAO`, `ProviderSubscriptionDAO`, `AiDailyUsageDAO`, `EmailActionDAO` (queries in `EmailActionQueries.ts`), `OAuth2AccessTokenCacheDAO`, `OAuth2AccessTokenRefreshStatusDAO`, `ApplicationIntegrationDAO`, `BackgroundTaskRunDAO`, `IntegrationDeliveryLogDAO`, `SyncedCalendarEventDAO`, `ActivityDAO`; `BaseDAO` generic helpers `findById`/`deleteOlderThan` (static) + instance variants `findRowById`/`deleteRowsOlderThanRows`/`encodeCursor`/`decodeCursor` (additive; new DAOs use instance variants); KV token cache; utils `D1SessionUtil`, `CursorUtil`, `D1ErrorClassifier`, `D1Utils`, `RepositoryHelper` (`pruneInBatches`, `computeUnixCutoffSeconds`, `computeDateCutoffIso`, `DEFAULT_PRUNE_BATCH_SIZE`); `CryptoService` (AES-GCM); `BaseDAO` is `@rexezuge/d1`'s sql-first base (`run/first/all(sql, [args])`) plus local `EncryptedDAO`, `findRowById`, `deleteOlderThan`, `assertSqlIdentifier`; constants `ProviderConfigKeys.ts` (single source for provider-config row keys). Per-app settings without columns (time zone, content language, features, filters, rules) → provider-config key/value rows.

**Why `UserDAO` is a subclass and not a re-export.** `users` here carries `preferred_language` (migration 0026), which the kit's DAO does not model, and it is a **user-facing setting**: `PUT /user/me` writes it, the SPA's language selector reads it back, and `ChatService` resolves the assistant's reply locale from it. Dropping the column to match the kit would be a product regression rather than a convergence. That is the escape hatch the kit's own migration table describes — a repo whose table has columns the kit's DAO does not model overrides the row instead of forking the kit.

`createUser` is overridden on top of that for a second, sharper reason. The kit's version is `INSERT … ON CONFLICT DO NOTHING` plus a read-back. D1 cannot alter a column's nullability, so every deployment predating migration 0028 has `users` rows with `id IS NULL`; against those, `DO NOTHING` treats the row as a conflict, creates nothing, and `registerAccount`'s opaque-anchor retry then mints a **second account beside the first**, orphaning every id-keyed row behind the original. The local `DO UPDATE … WHERE users.id IS NULL` means a conflict only ever _adopts_ an id-less row. The read-back is kept so the kit's `null` contract still holds and the retry is unaffected.

**Identity keys (migration 0028):** `users.email` is a **frozen anchor** — the PRIMARY KEY, the target of every legacy `FOREIGN KEY (user_email) REFERENCES users(email)`, and the input to the Vectorize namespace. Never `UPDATE` it. `users.id` is the stable account key; `users.current_email` the mutable sign-in address; `user_emails` the address registry. Migration 0029 adds `users.username` + its index for the kit's handle; nothing is backfilled (it is a public handle, not an identifier), and it is deliberately **not** unique — uniqueness is enforced in `setUsername` so two accounts swapping handles cannot transiently violate a unique index. 0028 is untouched: the kit's `USERS_SCHEMA` stays reference-only, because `applyIdentityMigrations` on an already-migrated database fails on `ADD COLUMN id` and silently leaves `username` unmigrated behind a `CREATE TABLE IF NOT EXISTS` no-op.

`user_id` is backfilled on `connected_applications`, `application_context_documents`, `application_context_deletion_runs`, `email_summary_actions` and `context_audit_logs`. Any new user-keyed table gets `user_id TEXT REFERENCES users(id)` and a `userScopeSql` predicate — a bare `user_email = ?` will 404 the owner after an address change.

Key provider-config rows: `calendar_time_zone`, `content_language`, `attachment_vision_enabled`, `sender_domain_filters`, `google_drive_page_token`, `onedrive_delta_link`, `digest_enabled`, `digest_send_time`, `digest_sections`, `digest_last_sent_at`.
